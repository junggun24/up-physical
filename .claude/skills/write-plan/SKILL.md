# 구현 계획 작성·실행

계획이 코드보다 중요하다 (시간 배분: 계획+검토 80%). 계획 없이 큰 작업을 시작하지 않는다.

## 1. 조사 (Plan의 절반)

- **코드베이스**: 유사 기능이 이미 어떻게 구현돼 있나 (패턴 재사용 우선).
- **하네스 지식**: 관련 `.harness/wiki/` + `.harness/solutions/` grep (같은 문제를 푼 적 있나).
- **외부**: 프레임워크·라이브러리의 권장 방식.

## 2. 설계 (소크라테스식 자문)

- 접근을 2개 이상 놓고 비교한다. **거절한 대안과 이유**를 기록한다.
- 엣지 케이스를 완료조건에 반영한다.
- 범위 도전: 더 작게 만들 수 없나? 이번에 안 만들어도 되나?

## 3. 계획 문서 작성

`.harness/plans/YYYY-MM-DD-<slug>.md` — 형식은 `plans/README.md`.
단계는 **체크포인트 단위**(각각 독립 검증 가능)로 쪼갠다. 리스크(가장 확신 없는 부분) 명시.

## 4. 승인

계획을 사용자/감독자에게 제시하고 **명시적 승인**을 받는다 (침묵 ≠ 동의).
승인 없이 Work 단계로 넘어가지 않는다.

## 5. 실행

- 체크포인트마다 검증(테스트/check.sh)하고 계획 문서에 진행 표시.
- 계획과 어긋나면 멈추고 계획을 갱신한다 (조용히 우회하지 않는다).
- 완료 후: 계획 vs 실제의 차이를 기록 → `harness-feedback` 환류.
